# Ingestor Microservice

## Methodology

### Overview

The Ingestor microservice serves as the automated content discovery entry point of the Sentinel pipeline. Unlike the other microservices, which are long-running stream consumers built on the `ServiceTemplate` base class, the Ingestor is designed as a **cron job** — a periodically scheduled, self-contained process that executes a full ingestion cycle and exits. This design is appropriate for its workload: bulk-polling of RSS feeds does not require persistent stream consumption logic, and a cron model naturally enforces a polling cadence without the overhead of a standing process.

### Periodic RSS Polling Architecture

On each execution, the Ingestor loads the RSS feed manifest from `rss_feeds.json`, validates it against a Pydantic schema (`List[RssSourceEntry]`), and categorises all feeds by payment tier (`FREE`, `METERED`, `PAYWALLED`). All feed URLs are flattened into a single list and passed to the `RssIngestor`, which executes the ingestion cycle via its `run()` method. The cycle proceeds through seven sequential steps: snapshot logging, article fetching, within-cycle deduplication, outlet attribution, Redis-filter deduplication, message construction and publishing, and statistics logging.

### Feed Configuration

The feed manifest (`rss_feeds.json`) defines 11 source entries totalling 157 feed URLs. Of these, **8 sources are active** — meaning they have at least one feed URL configured:

| Outlet        | Feeds | Payment Tier |
|---------------|-------|--------------|
| NPR           | 51    | FREE         |
| The Guardian  | 26    | FREE         |
| BBC           | 25    | FREE         |
| ABC           | 15    | FREE         |
| CBS           | 13    | FREE         |
| NBC           | 10    | FREE         |
| CBC           | 9     | FREE         |
| Euronews      | 8     | FREE         |

Three additional sources — **Associated Press** (FREE), **CNN** (METERED), and **Reuters** (METERED) — are present in the manifest but carry empty feed lists and therefore contribute zero URLs at runtime. CNN and Reuters are classified as `METERED`, reflecting the fact that their RSS feeds are either paywalled or rate-limited in a manner incompatible with high-frequency automated polling. The AP entry is classified `FREE` but has no feeds, suggesting it may be reserved for future integration. This tiered structure allows the system to declaratively manage source eligibility without modifying application logic.

### Concurrent Feed Fetching

The `RssIngestor.fetch_articles()` method uses Python's `concurrent.futures.ThreadPoolExecutor`, configured with `MAX_INGESTOR_WORKERS` threads, to fetch all 157 feeds in parallel. Each feed is retrieved via `feedparser.parse()` with a randomised user-agent string generated by the `user_agent_manager`, mitigating HTTP 403 responses from bot-detection systems. If a feed raises a `bozo_exception` (a feedparser signal for malformed XML) or any other exception, that feed is logged at `ERROR` level and skipped gracefully — ensuring a single unresponsive feed cannot abort the entire cycle. Successfully parsed feeds yield `Article` dataclass instances (containing `link`, `source`, `title`, and `summary`) via a generator.

### Within-Cycle Deduplication

Before consulting the persistent Redis filter, the `run()` method performs an in-process deduplication step by converting the list of raw `Article` objects into a Python `set`. Because `Article` is a frozen dataclass, equality and hashing are based on all fields, meaning URLs that appear across multiple feeds within the same cycle are deduplicated without any network round-trip. This step is critical given that NPR alone contributes 51 feeds, many of which share overlapping entries.

### Redis-Based Cross-Cycle Deduplication

The primary deduplication mechanism is a `RedisDuplicateFilter`, a wrapper around a persistent **Redis Set** (key name configured via `REDIS_DUPLICATE_FILTER_KEY`, TTL set to 0 — i.e., no expiry). After within-cycle deduplication, the filter's `has_many()` method is invoked with the full list of unique article URLs. Internally, this uses the Redis `SMISMEMBER` command, which checks membership for a batch of keys in a **single network round-trip** via a Redis pipeline. The method returns only those URLs not present in the set — the truly "unseen" articles. After publishing, the newly seen URLs are added to the set via `SADD` (batched with `add_many()`). Because the Redis Set is exact — unlike a Bloom filter, it produces no false positives — every URL that has ever been processed is permanently stored in memory. This is architecturally simple but has memory growth implications discussed in the Results section.

### Message Construction and Stream Publishing

For each unseen article, the Ingestor constructs a Pydantic `Message` object. The job UID is computed as the first 36 characters of the MD5 hash of the article URL, providing a stable, deterministic identifier that can be correlated across services. The `JobType` is set to `BACKGROUND`, and the initial `JobStage.INGESTED` timestamp is recorded. Messages are published in bulk to the `background:to.be.scraped` Redis Stream via `RedisPublisher.publish_many()`. The use of the **background priority lane** (as opposed to `user:to.be.scraped`) is deliberate: ingestor-driven content represents proactive, non-interactive discovery, and must not contend with latency-sensitive user-submitted jobs. The `ServiceTemplate`-based consumers downstream respect this priority separation through their `BlockPrioritisationLevel` configuration.

### Configuration and Error Handling

All tunable parameters are loaded via `common.env.get_env_var`, providing type-cast, fatal-on-missing semantics. Key variables include `MAX_INGESTOR_WORKERS` (parallelism), `REDIS_DUPLICATE_FILTER_KEY` (set name), `OUTPUT_STREAM` (target Redis stream), and PostgreSQL connection parameters for snapshot logging. Top-level exceptions in `main.py` are caught and written to `stderr` with a full traceback before exiting with code 1, ensuring cron daemon logs capture all failure information. Per-feed errors are isolated and do not propagate.

## Results & Analysis

### Long-Run Operational Performance (27 Days: February 25 – April 12, 2026)

Data collected over a 27-day operational period (with gaps corresponding to service downtime) provides the primary longitudinal baseline. Across this period, the Ingestor collectively processed **3,661,818 raw article URLs** from its 157 RSS feeds. Of these:

- **2,245,551** (61.3%) were eliminated in the within-cycle deduplication step — URLs appearing more than once across feeds within a single polling cycle.
- **1,391,974** (38.0%) of raw URLs had already been seen in a prior cycle and were rejected by the Redis filter.
- **24,293** (0.66% of raw) were genuinely new articles forwarded to the scraper.

The **cross-cycle Redis dedup rate** — computed as `seen / (seen + new)` — was **98.3%**, confirming that, at steady state, the overwhelming majority of URLs surfaced by RSS feeds are not new content. On fully operational days (those with approximately full ~168,000 URL throughput), the service averaged approximately **900 new articles per day**, or roughly one new article per 190 raw URL observations. The consistency of this figure across weeks indicates stable source publication rates.

Notably, days following extended service gaps (e.g., 2026-03-10 with 1,852 new; 2026-03-17 with 2,139 new; 2026-04-09 with 2,403 new) showed markedly elevated new article counts, as the Redis filter had not been updated during the outage period and newly published content had accumulated across sources. This demonstrates the correctness of the persistent Redis Set approach: the filter's memory does not decay during downtime.

### April 2026 Intensive Observation (April 15–18, 30 Cycles)

A higher-resolution dataset spanning 30 consecutive cycles collected across approximately four days provides cycle-level granularity. Key aggregate figures from this period are summarised below:

| Metric | Value |
|---|---|
| Total raw URLs fetched | 203,244 |
| After within-cycle deduplication | 100,999 (49.7% reduction) |
| Articles already in Redis filter | 99,568 (98.6% of deduplicated) |
| Genuinely new articles forwarded | 1,431 (0.70% of raw; 1.42% of deduplicated) |
| Average new articles per cycle | 47.7 |
| Average cycle execution time | 48.6 seconds |

The cycle execution time of approximately 49 seconds is attributable primarily to the concurrent HTTP fetching phase; at full 157-feed concurrency, network I/O is the dominant bottleneck. The within-cycle dedup rate of 49.7% reflects the high overlap between topically similar feeds (e.g., NPR's 51 feeds, many covering the same news categories).

**The Guardian** and **BBC** together accounted for 853 of the 1,431 new articles forwarded — **59.6% of all novel content** — despite representing approximately 46% of deduplicated volume. Their elevated novelty rates (1.90% and 1.73% respectively) reflect high publication frequency and broad topical coverage across their extensive feed portfolios (26 and 25 feeds respectively). NPR, despite contributing the largest raw feed count (51 feeds) and the third-highest deduplicated volume, exhibited the **lowest novelty rate at 0.64%**. This suggests that NPR's feeds exhibit strong topical overlap and that its high feed count does not translate proportionally to unique article discovery. CBS and NBC also showed below-average novelty rates (0.90% and 0.86%), consistent with broadcast networks whose online content is curated from a narrower editorial pool.

### Deduplication Rate Trends

Long-run data from `stats_old.json` shows a remarkably stable cross-cycle dedup rate, ranging from approximately 35–39% (as a fraction of raw URLs rejected by the Redis filter, not including within-cycle duplicates) across all operational days. Framed as the proportion of unique URLs already seen — the more meaningful metric — the rate consistently sits at **98.3–98.6%** across both the long-run and April datasets.

This stability has two implications. First, it confirms that the Redis Set–based deduplication mechanism is functioning correctly across extended operational periods: the persistent, TTL-free set retains all historical URLs without drift or expiry-related reprocessing. Second, it underscores the **efficiency of the ingestor as a pipeline gate**: 99.3% of raw HTTP observations are suppressed before reaching the scraper, preventing redundant scrape and NLP workloads for already-processed content.

### Infrastructure Growth Observations

Hourly database snapshots collected between April 15 15:32 and April 17 14:00 (approximately 47 hours) illustrate the infrastructure cost of the persistent-set deduplication strategy. **Redis memory grew from 504 MB to 2,488 MB** — an increase of approximately **1.82 GB** — reflecting the accumulation of URL strings in the set as three simultaneous team instances operated concurrently. PostgreSQL grew from **558 MB to 1,203 MB** (an increase of approximately **644 MB**) as new articles progressed through the NLP and retrieval pipeline to persistent storage.

The Redis growth rate observed during this period highlights a known architectural trade-off: the exact-membership Redis Set eliminates false positives entirely, but because `ttl_s=0` disables expiry, the set grows unboundedly over the system's lifetime. At production scale, this necessitates either periodic pruning, migration to a probabilistic structure (e.g., Redis Bloom Filter via RedisBloom module), or the use of a time-windowed key rotation strategy. For the current evaluation dataset, memory consumption remained within acceptable limits and no operational degradation was observed.

### Summary

The Ingestor microservice demonstrates effective design for high-volume, low-novelty RSS discovery. A sustained **98.3% cross-cycle deduplication rate** and average **~900 new articles per day** confirm that the service reliably gates the downstream pipeline against redundant work. The Guardian and BBC emerge as the primary sources of novel content, together contributing 59.6% of all forwarded articles. Cycle execution times of approximately 49 seconds are consistent and well within a practical cron scheduling interval. The primary architectural consideration for future scalability is the unbounded growth of the Redis deduplication set, which will require active management as the system matures beyond the evaluation period.
